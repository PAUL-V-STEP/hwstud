# hwstud — работа Claude Code с репозиторием

## 1. Назначение

Используй этот skill для задач в репозитории `hwstud`: анализ структуры, локальный запуск, изменения приложения, исправление ошибок, обновление документации, тестирование и подготовка выпуска.

Основное приложение находится не в корне Git, а в `hwstud-claude/`. Все команды приложения выполняй из этого каталога, если явно не указано иное. Рабочий язык проекта и отчётов — русский.

Skill не заменяет проектные инструкции. При противоречии соблюдай приоритет:

1. `hwstud-claude/CLAUDE.md`;
2. `hwstud-claude/REQUIREMENTS.md`;
3. `hwstud-claude/docs/07-AUTH-CLASS-CODE-KEYS.md` — по входу и регистрации;
4. `hwstud-claude/docs/04-HOSTING-REGRU.md`;
5. `hwstud-claude/docs/03-ARCHITECTURE.md`;
6. `hwstud-claude/docs/01-FUNCTIONS.md`;
7. `hwstud-claude/docs/02-DESIGN.md`;
8. `hwstud-claude/docs/05-HOMEWORK-UPLOAD.md`;
9. `hwstud-claude/docs/06-HELP.md`.

Перед содержательным изменением прочитай `hwstud-claude/CLAUDE.md` целиком, затем относящиеся к задаче документы. Не считай README доказательством production-готовности: сверяй заявления с кодом, тестами и фактическими проверками.

## 2. Неснимаемые ограничения

- Python 3.12, FastAPI, Jinja2, стандартный `sqlite3`, обычные SQL-миграции.
- Один процесс uvicorn с одним worker; фоновые задачи — внутри процесса через `asyncio` и таблицу `jobs`.
- Не добавляй ORM, PostgreSQL, Docker, Redis, Celery, Node.js, SPA-фреймворки, CDN, внешнюю аналитику и новые сервисы без явного разрешения пользователя.
- Новые Python-зависимости требуют отдельного согласования. В `requirements.txt` версии закрепляются точно.
- Внешние обращения приложения разрешены только к ProxyAPI и SMTP. Не добавляй другие исходящие запросы без изменения согласованных требований.
- Секреты находятся только в `.env`. Не запрашивай их в чат, не выводи в логи и не вставляй в код, тесты, документацию, коммиты или URL.
- Не выполняй платные запросы ProxyAPI без отдельного подтверждения. Не оплачивай услуги и не включай автопополнение.
- Не подключайся к серверу, не развёртывай и не публикуй сайт без отдельной явной просьбы пользователя.
- Не меняй согласованные функции, модель доступа, дизайн и требования по собственному усмотрению. Пробел сначала сформулируй и согласуй.
- Работай по одному этапу: локальный запуск/проверка, `pytest`, короткий русский отчёт. Следующий этап начинай после подтверждения пользователя.
- Не коммить и не отправляй изменения на GitHub автоматически. Для этого нужна просьба пользователя в текущей задаче.

## 3. Начало любой задачи

1. Определи корень Git и текущее состояние:

   ```bash
   git status --short
   git branch --show-current
   git log -5 --oneline
   ```

2. Прочитай текущий diff, если есть незакоммиченные изменения. Не перезаписывай чужую работу и не удаляй неотслеживаемые файлы.
3. Прочитай `hwstud-claude/CLAUDE.md` и документы по затрагиваемой области.
4. Найди фактические маршруты, сервисы, шаблоны, миграции и тесты. Не полагайся только на имена файлов или исторические отчёты.
5. Сформулируй минимальный объём изменения и проверку результата. Если задача затрагивает согласованные требования, сначала спроси.
6. Перед правками проверь, нет ли уже реализации или теста для требуемого поведения.

## 5. Локальный запуск

### 5.1. Windows

Из `hwstud-claude/`:

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m app.tools.init_local
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Если `.venv` уже существует, не создавай его заново. `init_local` создаёт локальный `.env` только при его отсутствии, генерирует секрет сессии без вывода, создаёт каталоги и применяет миграции.

Открой `http://127.0.0.1:8000`. Проверка liveness: `GET /health`. Этот ответ не подтверждает готовность БД, Worker, SMTP, ProxyAPI или восстановления.

Первичный вход преподавателя и обязательную смену пароля выполняй по `hwstud-claude/README.md`. Не публикуй сайт с начальным паролем.

### 5.2. Linux

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m app.tools.init_local
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Production-команда отличается: используй `deploy/hwstud.service`, `--proxy-headers`, отдельного пользователя и `/opt/hwstud/.env`. Не переноси локальный `.env` на сервер.

### 5.3. Правила запуска

- Держи только один worker: встроенные очередь, расписание, лимиты и карточки доступа рассчитаны на один процесс.
- Не запускай второй экземпляр на той же БД без необходимости.
- Не удаляй `data/`, SQLite WAL/SHM или `.env` для устранения ошибки без понимания последствий и резервной копии.
- Для диагностики без фонового цикла используй тестовый механизм `ENABLE_WORKER`, как в `tests/conftest.py`; не отключай Worker в production ради скрытия ошибки.
- Проверяй реальные ProxyAPI/SMTP только по отдельному сценарию и с согласия пользователя.

## 6. Внесение изменений

### 6.1. Общий порядок

1. Воспроизведи текущее поведение или зафиксируй требование.
2. Найди минимальный затрагиваемый контур: route → service → DB/template → tests.
3. Сохрани существующие архитектурные соглашения и русские тексты интерфейса.
4. Добавь регрессионный тест до или вместе с исправлением.
5. Выполни точечный тест, затем полный `pytest`.
6. Проверь ручной сценарий, если изменение затрагивает браузер, файлы, очередь или внешнюю интеграцию.
7. Обнови соответствующую документацию и дай отчёт: что изменено, что проверено, что осталось.

### 6.2. Backend и БД

- Изменяющие данные формы используют POST и CSRF. Не вводи GET-мутации для новых действий.
- Сохраняй серверную проверку роли, группы, владельца объекта и экзамена; скрытие ссылки в HTML не является авторизацией.
- Не возвращай чужие работы, переписку, преподавательские тексты, секреты или открытые ключи.
- Для конкурентных изменений используй подходящую транзакцию `BEGIN IMMEDIATE`; проверку лимита и запись выполняй атомарно.
- Новую миграцию создавай со следующим свободным номером после проверки каталога `migrations/`, а не по памяти.
- Миграция должна применяться на чистой и существующей БД, иметь тест и не уничтожать данные без согласованного сценария.
- Время храни в UTC, на экране показывай Europe/Moscow.
- Не добавляй автоматический повтор уже отправленного платного GPT-запроса после перезапуска. Ручной повтор должен явно обозначать возможную новую оплату.
- Синхронные тяжёлые вызовы выноси через `asyncio.to_thread`; единые семафоры должны действовать и для Worker, и для HTTP-операций.

### 6.3. Frontend

- Сохрани серверный рендеринг и работоспособность основных страниц/форм без JavaScript.
- JavaScript — только небольшой локальный progressive enhancement в разрешённых проектом случаях.
- Не подключай CDN, внешние шрифты, библиотеки, счётчики и аналитику.
- Соблюдай `docs/02-DESIGN.md`: две темы, русский тон, текст не менее 14 px, контраст WCAG AA, клавиатура, видимый фокус и `prefers-reduced-motion`.
- Проверяй мобильную навигацию без горизонтальной прокрутки страницы, возврат из форм и отсутствие преподавательского HTML у студента.
- При изменении общих CSS/JS обнови версию их URL по действующему правилу проекта.
- Ограничение первой загрузки без слайдов — 300 КБ сжатого трафика; проверяй его отдельно после изменения общих ресурсов.

### 6.4. Тесты

Из `hwstud-claude/`:

```powershell
.venv\Scripts\python.exe -m pytest
```

Точечный запуск:

```powershell
.venv\Scripts\python.exe -m pytest tests\test_submissions.py
.venv\Scripts\python.exe -m pytest tests\test_web_auth.py -k "имя_сценария"
```

Linux: замени интерпретатор на `.venv/bin/python`.

- Все внешние сервисы в автоматических тестах заменяй заглушками; сетевых вызовов быть не должно.
- Не меняй ожидаемый результат теста только ради зелёного прогона: сначала определи, какая сторона ошибочна — код или устаревшее требование.
- Для исправления ошибки добавь сценарий, который падает на прежнем поведении и проходит после исправления.
- Для доступа проверяй владельца, другого студента, другую группу, преподавателя и отсутствие сессии.
- Для конкурентности проверяй фактическое число запросов/строк, а не только отсутствие исключения.
- Зафиксируй в отчёте число тестов, warnings и время только по реальному выводу текущего запуска.

## 8. Диагностика ошибок

Сначала сохрани полный traceback/HTTP-статус/условия воспроизведения, затем сузь причину. Не маскируй ошибку широким `except`, повторными платными запросами или отключением защиты.

| Симптом | Порядок проверки |
|---|---|
| `SESSION_SECRET не задан` | Выполни `python -m app.tools.init_local`; проверь наличие `.env`, не выводя его содержимое |
| `ModuleNotFoundError` | Проверяется ли Python 3.12 из `.venv`, установлены ли `requirements.txt`, из какого каталога запущена команда |
| Порт 8000 занят | Найди существующий локальный процесс; не завершай неизвестный процесс и не запускай второй worker на той же БД |
| `database is locked` | Проверь длительные транзакции, параллельные тяжёлые операции, отдельные подключения потоков и `busy_timeout`; не удаляй WAL |
| Ошибка миграции | Проверь `schema_version`, порядок SQL, чистую и существующую копию БД; перед исправлением сохрани резервную копию |
| 401/403 ProxyAPI | Проверь ключ и доступ модели через безопасный сценарий; останови новые GPT-задачи по проектным правилам |
| 402 ProxyAPI | Нет средств: сохраняй очередь и паузу; не включай пополнение и не повторяй запросы автоматически |
| 429/5xx/тайм-аут ProxyAPI | Учитывай проектную политику повторов и возможность повторной оплаты; проверь `request_sent_at` и бюджет |
| Модель не подтверждена | Проверь `models_confirmed` и актуальность конфигурации; реальная проверка — только по команде ниже с подтверждением |
| SMTP недоступен | Сообщение должно остаться в БД/очереди; проверь host, port 465/587, SSL/STARTTLS и задания `mail`, не раскрывая пароль |
| Отклонён DOCX/PPTX/PDF | Сверь фактический формат, ZIP-лимиты, страницы, пиксели и время разбора; не повышай защитные лимиты без согласования |
| Старые CSS/JS в браузере | Проверь версию URL общих ресурсов и кеш Caddy/браузера; не отключай CSP |
| 423/429 при входе | Проверь сработавший лимит и блокировку ника; не ослабляй защиту ради прохождения теста |
| Падает только полный набор | Ищи общее состояние, временные каталоги, порядок тестов и Worker; затем точечный тест и полный прогон |

Реальная проверка моделей может быть платной. Выполняй только после отдельного подтверждения пользователя и при уже настроенном пользователем ключе:

```powershell
.venv\Scripts\python.exe -m app.tools.check_models --confirm-paid
```

Без `--confirm-paid` сетевых запросов нет. Не запускай эту команду как обычный тест.

## 9. Контроль известных рисков перед первым выпуском

Этот список отражает анализ текущего кода на момент создания skill. Перед использованием проверь актуальность каждого пункта по коду; не считай проблему существующей или исправленной только по этому списку.

1. Ограничены ли число референсов, пакетов, совокупный контекст и стоимость similarity в `app/services/grading.py`; покрывает ли резерв `app/services/balance.py` реальный worst case.
2. Отзываются ли все админские сессии после смены пароля в `app/auth.py`; безопасен ли первичный вход до публикации.
3. Сохраняются ли почтовые задачи других студентов при удалении ника в `app/services/students.py`.
4. Используют ли экспорты, ручные backup/check и сохранение лекции общий `heavy`-семафор, а не только Worker.
5. Записываются ли просмотры в `slide_views`; достоверны ли прогресс и связанная часть SWOT.
6. Реализованы ли диаграмма Ганта, оглавление, поиск по лекциям, ссылки на слайды и 15-минутный предел импорта.
7. Выбирают ли результаты последнюю попытку с решением преподавателя, а не `MAX(id)` любого статуса; привязан ли разбор к отображаемой попытке.
8. Связано ли подтверждение моделей с их именами и параметрами, а не только с булевым `models_confirmed`.
9. Создаёт ли ручная резервная копия действительно свежий файл вместо возврата существующего файла даты.
10. Атомарна ли проверка суточного лимита сообщений вместе со вставкой.
11. Есть ли политика хранения prepared JSON, uploads, jobs и архивов; не переполняют ли они диск.
12. Удалены ли устаревшие надписи ранних этапов из действующих шаблонов и README.

Для каждого подтверждённого дефекта нужен отдельный regression test. Закрытый пункт фиксируй в `TESTING.md` с фактической проверкой.

## 10. Подготовка к публикации

Сначала различи тип публикации:

- **GitHub:** коммит и push текущей ветки после явной просьбы пользователя. Это не развёртывание сайта.
- **Production:** отдельная операция на Linux/VPS по `DEPLOY.md`, только после явной просьбы и завершения серверной приёмки.

### 10.1. Обязательный локальный release-checklist

1. Проверь назначение изменений:

   ```bash
   git status --short
   git diff --check
   git diff --stat
   ```

2. Изучи итоговый diff и убедись, что в него не попали посторонние отчёты, рабочие данные, временные файлы и несвязанные правки.
3. Выполни полный `pytest` на Python 3.12. Зафиксируй фактический результат.
4. Запусти локальный сервис и проверь изменённый критический сценарий. `/health` недостаточно для release readiness.
5. Проверь `git ls-files`: в индексе не должно быть `.env`, `.venv/`, `data/`, SQLite/WAL, рабочих архивов, секретов и персональных данных. Не выводи значения возможных секретов в отчёт.
6. Проверь `.env.example` и `deploy/hwstud.env.example`: только пустые или безопасные значения.
7. Проверь миграции на чистой БД и копии существующей БД, если они изменялись.
8. Обнови README, `TESTING.md` и профильную документацию; синхронизируй заявления с фактически выполненными проверками.
9. Перечисли оставшиеся ручные, серверные, платные и нагрузочные проверки отдельно. Не выдавай их за выполненные.
10. Перед коммитом проверь `git diff --cached --check` и состав staged-файлов. Используй требуемые текущей сессией attribution-строки, не пропускай hooks и не меняй историю без просьбы.

### 10.2. Дополнительная production-приёмка

Выполняется только в согласованной серверной среде:

- `caddy validate` и `systemd-analyze verify` для фактических конфигов;
- один uvicorn worker, непривилегированный пользователь, `MemoryMax=1200M`, закрытый снаружи порт 8000;
- миграции на резервной копии, HTTPS, security headers и отсутствие публичного `data/`;
- реальные SMTP и модели по отдельным согласованным сценариям;
- импорт лекции + два предельных DOCX + две проверки с измерением памяти;
- свободное место, предупреждение диска, запрет небезопасного архива;
- свежая резервная копия, её независимое хранение и реальное восстановление;
- основные страницы без JavaScript, отсутствие внешних браузерных запросов и лимит 300 КБ;
- критические сценарии доступа, четырёх попыток, одобрения, разбора, экзамена и удаления данных.

Если хотя бы один обязательный пункт не выполнен, явно запиши это в release-отчёт и не называй production-приёмку завершённой.

## 11. Критерий завершения задачи

Задача считается завершённой только когда:

- изменение соответствует проектным документам и не нарушает ограничения;
- доступ, CSRF, приватность и платные запросы проверены по затронутому контуру;
- точечные и полные тесты выполнены с честно указанным результатом;
- ручной сценарий выполнен, если автоматический тест его не покрывает;
- README и профильные документы обновлены без завышения готовности;
- diff не содержит секретов, рабочих данных и посторонних файлов;
- оставшиеся риски и невыполненные проверки перечислены;
- коммит/push/production выполнены только при явном разрешении и перечислены отдельно в отчёте.
