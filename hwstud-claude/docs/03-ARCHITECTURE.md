# Архитектура сайта hwstud.ru

Финальная версия 2.1 от 23.11.2026. Как реализовать функции из `01-FUNCTIONS.md` (финальная версия 2.1) минимальным набором инструментов.

## 1. Разрешённый стек

| Слой | Инструмент | Зачем |
|---|---|---|
| Язык | Python 3.12 (есть в Ubuntu 24.04) | Всё приложение |
| Веб | FastAPI + uvicorn | Маршруты, формы, загрузка файлов |
| Шаблоны | Jinja2 | Страницы собираются на сервере |
| Формы | python-multipart | Загрузка файлов |
| Сессии | itsdangerous (через `SessionMiddleware` Starlette) | Подписанная cookie |
| База | SQLite, модуль `sqlite3`, режим WAL | Одна база-файл, без ORM |
| HTTP-клиент | httpx | Запросы к ProxyAPI — и только к нему |
| PPTX | python-pptx (вместе с lxml и Pillow) | Заметки, заголовки, разделы слайдов |
| PDF | PyMuPDF | Картинки слайдов, текст работ студентов, выгрузка PDF |
| DOCX | python-docx | Текст и структура DOCX работ студентов, выгрузка DOCX |
| XLSX | openpyxl | Выгрузка глоссария в Excel |
| Почта | `smtplib` и `email` из стандартной библиотеки | Письма преподавателю |
| HTTPS | Caddy | Сертификат Let's Encrypt автоматически, раздача статики |
| Запуск | systemd | Автозапуск и перезапуск приложения |
| Тесты | pytest | Только для разработки |

Файл `requirements.txt` содержит только эти пакеты с закреплёнными версиями. Новые пакеты — только с разрешения пользователя.

**Внешние обращения сервера:** только `api.proxyapi.ru` (HTTPS) и SMTP-сервер ящика преподавателя. Сервер не открывает ссылки литературы и любые другие внешние адреса. Обращение к Let's Encrypt делает Caddy.

**Шрифты.** IBM Plex Sans и IBM Plex Mono (лицензия OFL) скачиваются один раз при разработке из официального репозитория IBM:

- `static/fonts/*.woff2` — для браузера, кириллица и латиница;
- `app/fonts/*.ttf` — для выгрузок PDF: PyMuPDF встраивает TTF, кириллица отображается без системных шрифтов.

## 3. Модель данных (SQLite)

Миграции — простые SQL-файлы. Таблица `schema_version` хранит номер последней применённой миграции. Первая миграция создаёт 4 группы «Группа 1» … «Группа 4».

При создании **каждого** подключения в `db.py` выполняются `PRAGMA foreign_keys = ON`, `PRAGMA secure_delete = ON` и `PRAGMA busy_timeout = 5000`. Режим WAL также настраивается на каждом подключении. Это важно для удаления персональных данных и согласованной работы потоков.

| Таблица | Главные поля |
|---|---|
| `groups` | id, name, max_members (20), enroll_open |
| `students` | id, group_id, nick, nick_norm (нижний регистр, уникальный), created_at, blocked, login_token. ФИО и контакты не хранятся |
| `lectures` | id, slug (уникальный), num, title, title_norm (уникальный индекс), status (hidden/open), planned_date, announce, header_lines, files_dir, updated_at |
| `lecture_groups` | lecture_id, group_id — пусто означает «все группы» |
| `lecture_sections` | lecture_id, idx, title, first_slide |
| `slides` | lecture_id, n, title, notes_html, img, thumb, section_idx, missing_notes |
| `slide_views` | student_id, lecture_id, n, viewed_at |
| `imports` | id, created_at, ready_at, status (processing/waiting_gpt/paused_no_funds/ready/saving/saved/expired/cancelled/failed), target_lecture_id, version_dir, report_json |
| `terms` | id, term, expansion, english, status (draft/verified/hidden), unused |
| `term_refs` | term_id, lecture_id, slide_n |
| `term_conflicts` | term_id, lecture_id, slide_n, variant |
| `sources` | id, author, title, url, type, annotation, priority (main/extra) |
| `source_refs` | source_id, lecture_id, slide_n, local_number |
| `assignments` | стабильный id (1–10), position (текущий номер и порядок), title, condition, reference, criteria, typical_errors, threshold (0,7), due_at, max_attempts (4) |
| `submissions` | id, student_id, assignment_id, attempt, file, mime, size, pages, chars, created_at, late, status, verdict, score (0–10), comment, errors_json, classification, confidence, similarity_json, decided_at |
| `review_requests` | id, submission_id, question, created_at, status (open/answered), answer (последний ответ, для совместимости) |
| `review_messages` | id, request_id, author (student/teacher), body до 2000 знаков, created_at; каскадно удаляется вместе с запросом |
| `jobs` | id, kind, priority, payload_json, status, tries, run_after, started_at, request_sent_at, error, model, tokens_in, tokens_out, cost_est |
| `announcements` | id, title, body, link, kind (normal/important/deadline), pinned, publish_at, unpublish_at |
| `announcement_groups` | announcement_id, group_id — пусто означает «все группы» |
| `announcement_reads` | announcement_id, student_id, read_at |
| `messages` | id, student_id, author (student/teacher), body, ref_lecture, ref_slide, ref_assignment, created_at, teacher_read_at, student_read_at, mailed_at |
| `threads` | student_id (одна ветка на ник), closed_at |
| `exam` | одна строка: enabled, start_at, end_at |
| `exam_groups` | group_id — пусто означает «все группы» |
| `settings` | key, value — общие настройки из админки: пороги баланса, цены моделей, ссылка на пополнение, режим писем, текст страницы «О курсе» |
| `balance_log` | id, at, balance, budget_limit, budget_used, source (poll/manual/probe) |
| `balance_state` | одна строка: level (ok/low/critical/no_funds/unknown), paused, paused_since, balance_access (allowed/denied/unknown), last_ok_at, last_error, gpt_stopped (ключ отклонён) |
| `balance_alerts` | level, sent_at |
| `audit_log` | id, at, actor, action, object, student_id (если действие связано со студентом), details_json |
| `maintenance` | одна строка: deletion_step (null/db_deleted/db_done/backup_done/files_done), started_at — состояние удаления данных студентов |

**Одно место для итогового вердикта.** Поля `verdict`, `score`, `comment`, `errors_json` в `submissions` хранят последний вердикт. Сначала их заполняет ИИ, при решении преподавателя они перезаписываются. Отдельной истории и полей «вердикт ИИ / вердикт преподавателя» нет — так решил пользователь.

## 4. Статусы работы

```
not_submitted ──загрузка──▶ queued ──взята──▶ checking ──ответ ИИ──▶ awaiting_approval
                              ▲                  │                        │
                              │ 402 / пауза      │ низкая уверенность,   │ преподаватель
                              └──────────────────┤ ошибка, нет JSON      │ «Одобрить»
                                                 ▼                        ▼
                                           needs_review ──решение──▶ accepted | revise
                                                                          │
                                         revise и attempt < 4 ──▶ можно загрузить новую попытку
                                         revise и attempt = 4 ──▶ exhausted (конец)
```

| Внутренний статус | Студент видит | Видит вердикт и баллы |
|---|---|---|
| `not_submitted` | Не сдано | — |
| `queued`, `checking`, `awaiting_approval`, `needs_review` | На проверке | Нет |
| `revise` | На доработку | Да |
| `accepted` | Принята | Да |
| `exhausted` | Попытки исчерпаны | Да |

- Пауза из-за баланса — свойство задачи в `jobs` (`paused_no_funds`), а не работы: работа остаётся `queued`.
- Переходы выполняет одна функция `submissions.transition(sub, new_status)`. Недопустимый переход — исключение и тест.
- Новая попытка — новая строка в `submissions` с `attempt + 1`. Загрузка разрешена только если последняя попытка в статусе `revise` и `attempt < 4`.

## 5. Доступ: одна функция на всё

Все проверки «можно ли студенту видеть» собраны в `access.py`. Маршруты, поиск, глоссарий, литература и картинки слайдов вызывают только её.

```
exam_active(group, now) =
    exam.enabled
    and (exam.start_at is null or now >= exam.start_at)
    and (exam.end_at is null or now < exam.end_at)
    and (exam_groups пусто or group in exam_groups)

content_visible(student, now) = not exam_active(student.group, now)

lecture_visible(student, lecture, now) =
    content_visible(student, now)
    and lecture.status == "open"
    and (lecture_groups пусто or student.group in lecture_groups)
```

- Лекции открываются только вручную: поля даты открытия нет. `planned_date` — справочное, на доступ не влияет.
- Анонс: если лекция скрыта и `announce` включён, в списке показываются только название и `planned_date`.
- Глоссарий, литература и поиск при `content_visible = False` закрыты полностью. Вне экзамена термин или источник виден, только если у него есть ссылка на видимую студенту лекцию. Номера слайдов показываются только из видимых лекций.
- **Иллюстрация закрытого доступа:** серверный шаблон закрытого раздела подключает только локальные JPG из `static/images/`: `content-closed-96.jpg` для компактной плашки и `content-closed-640.jpg` для полноценного экрана. Вариант 960 px допускается через `srcset` для экранов с высокой плотностью пикселей только после прохождения проверки общего веса страницы 300 КБ. Исходный PNG 6,2 МБ в HTML не включается. У `<img>` задаются квадратные `width`/`height`, `decoding="async"` и альтернативный текст из `02-DESIGN.md`, раздел 2.5.1; JavaScript и внешние запросы не нужны. Обычные скрытые лекции и ошибки 404 эту иллюстрацию не используют.
- Задания, объявления и переписка от `content_visible` не зависят.
- Страницы `/help` и `/help/upload` доступны студенту и преподавателю после входа и также не зависят от `content_visible`. Студент получает только студенческую версию. Преподаватель получает обе версии с переключателем «Студенту / Преподавателю»; выбор преподавательской версии разрешён только его сессии. Ролевой шаблон выбирается на сервере: студенческий HTML не содержит преподавательских текстов, а прямой запрос студента к преподавательской версии возвращает 404. Доступ к ролевым версиям проверяет `access.py`; содержание страниц — `docs/06-HELP.md`.
- **Файл работы** `/u/<submission_id>`: отдаётся, только если `submission.student_id` = студент сессии или это сессия преподавателя. Иначе 404, без подсказки, что файл существует.
- **Диалог разбора** `/reviews/<request_id>` доступен только студенту — владельцу связанной работы; `/admin/review-requests/<request_id>` — только преподавателю. Иначе 404. Создание требует непустого `question`; сообщения обеих ролей непустые и до 2000 знаков. Ответ преподавателя добавляет строку `review_messages` и ставит запросу `answered`; уточнение студента добавляет строку и возвращает `open`.
- **Ссылка на лекцию в объявлении:** если `lecture_visible = False`, шаблон выводит название серым текстом без ссылки: «пока недоступна» или при `exam_active` — «закрыто на время экзамена».
- **Страница `/about`** без входа показывает только названия лекций со `status = open` (для любой группы).
- **Анонс:** включить `announce` можно только при заполненном `planned_date`; проверка в форме и в коде сохранения.
- Преподаватель видит всё. «Режим студента» — флаг в сессии преподавателя: страница строится тем же кодом, что у студента, проверка `lecture_visible` пропускается только для выбранной лекции и только для сессии преподавателя.

## 6. Вход

- **Студент:** форма «ник» → если ника нет, выбор группы. Других полей нет.
- **Нормализация ника:** `strip()`, затем проверка по шаблону `^[A-Za-z0-9_-]{3,24}$`. В `nick_norm` хранится `lower()`, уникальный индекс по `nick_norm`. Показывается ник в том виде, как его ввели.
- **Проверки при создании ника:** группа заполнена меньше чем на 20, набор в группу открыт, `nick_norm` свободен.
- **Сессия:** подписанная cookie на 90 дней, `HttpOnly`, `Secure`, `SameSite=Lax`, внутри `student_id` и `login_token`. Блокировка ника или смена `login_token` в админке выходит из всех устройств.
- Вход по нику без пароля — осознанное решение пользователя. Защита от перебора: не больше 20 попыток входа с одного IP в час.
- **Преподаватель:** пароль сравнивается с хешем `scrypt` (модуль `hashlib`) из `.env`. Не больше 5 ошибок за 15 минут с одного IP.
- Все формы, меняющие данные, — POST со скрытым CSRF-токеном из сессии.

## 7. Загрузка лекции

1. Преподаватель загружает PPTX и PDF одной формой, каждый до 40 МБ. Приложение проверяет размер каждого файла и отклоняет больший. Ограничения распаковки и времени разбора — раздел 7.1. Одновременно допускается не больше 5 импортов в статусах `processing`, `waiting_gpt`, `paused_no_funds`, `ready`, `saving`, суммарно не более 1 ГБ в `data/import/`. Проверка квоты и создание импорта выполняются в одной транзакции `BEGIN IMMEDIATE`.
2. Создаётся запись `imports` и задача `jobs` вида `lecture_import`. Разбор идёт в фоне (раздел 10), страница показывает прогресс.
3. `lecture_import.py`:
   - PDF → картинки страниц через PyMuPDF, постранично: WebP шириной 1600 px и миниатюра 320 px, качество 80;
   - PPTX → заголовок слайда, текст заметок, разделы из `p14:sectionLst` в `ppt/presentation.xml` (через lxml);
   - заметки: первая строка жирным — заголовок текста, дальше абзацы; строки «Сокращения: …» отделяются для глоссария; номера `[n]` и строки источников — для литературы;
   - повторяющиеся служебные строки (больше чем на половине слайдов, порог из настроек) переносятся в `header_lines`.
4. **Сравнение заголовков PPTX и PDF** (предупреждение, не блокировка): обе строки приводятся `unicodedata.normalize("NFKC")` → удаляются мягкие переносы `U+00AD` и неразрывные пробелы → `ё` заменяется на `е` → нижний регистр → все пробельные символы и переносы строк схлопываются в один пробел → знаки препинания удаляются. Заголовок считается найденным, если он содержится в тексте страницы.
5. **Блокирующие проверки и предупреждения** — `01-FUNCTIONS.md`, раздел 2.1. Блокирующие показываются на экране предпросмотра, кнопка «Сохранить на сайте» неактивна.
6. **Задачи GPT при импорте** (модель `MODEL_AUX`, приоритет 4):
   - `parse_abbr` — сложные строки «Сокращения: …», где внутри расшифровки есть «;». Отправляются только эти строки. Ответ: `{"items": [{"term": "", "expansion": "", "english": ""}]}`.
   - `abbr_guess` — поиск сокращений без расшифровки. Кандидаты находит код: слова из 2–10 заглавных латинских или кириллических букв, цифр, `&` и `-`, которых нет ни в глоссарии, ни в блоках «Сокращения:» этой лекции. У каждого кандидата отправляется одно предложение контекста. Кандидаты делятся на пакеты не более чем по 60; создаются задачи для **всех** пакетов, никакие кандидаты не пропускаются. Ответ в том же формате, все расшифровки получают статус `draft` («черновик — проверить»).

   Пока эти задачи не завершены, `imports.status = waiting_gpt`, при паузе баланса — `paused_no_funds`. Сохранение возможно только при `ready`. Обе задачи блокируют сохранение — так решил пользователь. Завершёнными считаются все пакеты, включая обработанные с предупреждением о неразобранных сокращениях.
7. **Определение лекции для обновления:** `title_norm` (та же нормализация, что в п. 4) сравнивается с сохранёнными лекциями. `title_norm` уникален, поэтому совпадение бывает не больше одного. Совпадение → предложение «Обновить лекцию «…»», преподаватель подтверждает. Нет совпадения → новая лекция, `slug` = транслитерация названия латиницей (ГОСТ 7.79, система Б), нижний регистр, дефисы, до 60 знаков; при занятом `slug` добавляется `-2`, `-3`. Обновление заменяет слайды, разделы, заметки и ссылки глоссария и литературы этой лекции, но сохраняет `status`, группы, `planned_date`, `announce`, `slug`.
8. **«Сохранить на сайте»** — база и файлы меняются так, чтобы сбой в любой момент не оставил лекцию наполовину обновлённой:
   1. Отдельной транзакцией фиксируются `imports.status = saving` и `imports.version_dir = data/lectures/<slug>/v<import_id>/`.
   2. Картинки слайдов переносятся из `data/import/<id>/slides/` в `version_dir` (перенос `os.replace` внутри одного диска).
   3. Одна транзакция SQLite: заменяются слайды, разделы, ссылки глоссария и литературы, `lectures.files_dir = version_dir`, `imports.status = saved`.
   4. После commit удаляется прежняя папка версии и `data/import/<id>/`.
   - До commit студенты видят старую версию, после — новую. Маршрут картинок берёт папку из `lectures.files_dir`.
   - **Восстановление при старте, если импорт остался в `saving`:** значит, транзакция из п. 3 не зафиксирована. Если `version_dir` существует и не используется ни одной лекцией, его сначала возвращают `os.replace` обратно в `data/import/<id>/slides/`. Затем импорт получает статус `ready`, `version_dir = null`. Только после восстановления всех таких импортов разрешается удалять прочие папки `v*`, не связанные ни с лекциями, ни с активными импортами. Если commit успел выполниться, импорт уже имеет статус `saved`, новая папка связана с лекцией и не удаляется.
   - Обязательный тест: остановить процесс после `os.replace`, но до commit, перезапустить и сохранить лекцию без повторной загрузки PPTX/PDF.
9. **Срок хранения и очистка:**
   - `processing`, `waiting_gpt`, `paused_no_funds` хранятся до завершения или отмены преподавателем, без срока, но в пределах общей квоты из п. 1.
   - `ready` хранится 7 дней от `ready_at`. На экране предпросмотра: «Предпросмотр хранится до <дата>». Потом статус `expired`, кнопка «Сохранить на сайте» неактивна, лекцию нужно загрузить заново.
   - Ночная очистка удаляет папки `data/import/<id>/` только у импортов `saved`, `expired`, `cancelled`, `failed`. Исходные PPTX и PDF удаляются вместе с папкой.

### 7.1. Защита от слишком больших файлов

Размер файла ограничивает только упакованный объём. PPTX и DOCX — архивы ZIP, поэтому до разбора приложение читает их оглавление через `zipfile` и отклоняет файл без распаковки, если:

| Что | PPTX лекции | DOCX работы |
|---|---|---|
| Сумма распакованных размеров | 300 МБ | 50 МБ |
| Элементов в архиве | 5000 | 1000 |
| Степень сжатия любого элемента | больше 100 : 1 | больше 100 : 1 |

- PDF лекции — не больше 300 страниц; PDF работы читается постранично и прекращается, как только превышены 30 000 знаков, 5 страниц-сканов или 50 страниц всего.
- Картинки: `Image.MAX_IMAGE_PIXELS = 40_000_000` (Pillow), больше — отказ.
- Кооперативный лимит времени разбора: работа — 60 с, лекция — 15 мин. Время проверяется между вызовами библиотек и внутри циклов по страницам и слайдам; после возврата управления превышение даёт отказ с сообщением «Файл не удалось прочитать за отведённое время».
- Жёсткий тайм-аут на один блокирующий вызов `fitz.open`, `python-pptx`, `python-docx` или рендер страницы не обещается: поток в Python принудительно не прерывается, отдельные процессы-воркеры запрещены. До вызова библиотек обязательно применяются лимиты ZIP, страниц и пикселей, а в `TESTING.md` добавляются повреждённые и чрезмерно сложные файлы.

Картинки слайдов отдаёт приложение по маршруту `/l/<slug>/s/<n>.webp` после проверки доступа, с заголовком `Cache-Control: private, max-age=3600`. Прямого доступа к `data/` через Caddy нет.

## 8. Агент проверки

### 8.1. Модели

| Задача | Модель | Цена на 22.11.2026, ₽ за 1 млн токенов (ввод / вывод) | Ограничение ответа |
|---|---|---|---|
| Проверка работ | `openai/gpt-6.1-terra` | 260 / 1300 | 1500 токенов |
| Разбор сокращений, тип и аннотация источника | `openai/gpt-6-luna` | 30 / 150 | 2000 токенов |

Обе модели в каталоге ProxyAPI отмечены как поддерживающие изображения и JSON ([ProxyAPI, модели OpenAI](https://www.proxyapi.ru/models/openai)). Каталог не уточняет, что именно означает отметка «JSON». Поэтому на этапе 1 есть обязательный проверочный скрипт `python -m app.tools.check_models`. Он выполняет для каждой модели два запроса с одинаковым текстом: текстовый и с фиксированной тестовой картинкой 1600 × 1600 px. В обоих проверяются `response_format` типа `json_schema` и `max_completion_tokens`. Если `json_schema` не принят, код переходит на `response_format: {"type": "json_object"}` и проверку ответа по схеме в коде. Проверочные запросы могут быть платными; прикладные запросы начинаются только после успешной проверки.

`image_tokens` определяется из отдельного поля детализации `usage`, если ProxyAPI его предоставляет. Иначе используется разность `usage.prompt_tokens` запроса с картинкой и идентичного текстового запроса. Если разность получить нельзя, сохраняется консервативное значение по умолчанию 1500 с пометкой «оценка». Размер и пропорции тестовой картинки, способ измерения и результаты записываются в `TESTING.md`; для других пропорций значение также считается оценкой и покрывается `reserve_factor`. Если модель не принимает картинки или JSON, скрипт останавливает работу с сообщением: пользователь выбирает другую модель. Цены преподаватель отдельно сверяет с каталогом ProxyAPI, поскольку запрос к модели их не подтверждает.

Модели задаются в `.env` (`MODEL_GRADING`, `MODEL_AUX`), цены — в настройках админки (для оценки расхода).

### 8.2. Подготовка работы

| Тип файла | Что отправляется | Ограничение (иначе отказ при загрузке) |
|---|---|---|
| PDF | Каждая страница отдельно: страница с 200 знаками текста и больше — текстом, с меньшим — картинкой 1600 px по длинной стороне. Смешанный PDF отправляется текстом и картинками в порядке страниц | Текст до 30 000 знаков, страниц-картинок до 5, всего до 50 страниц |
| JPG, PNG | Одна картинка, 1600 px по длинной стороне | 1 изображение |
| DOCX | Текст через python-docx и изображения JPEG/PNG из тела документа в порядке их следования; каждое изображение — не более 1600 px по длинной стороне | До 30 000 знаков текста и до 5 изображений JPEG/PNG |
| TXT | Текст в UTF-8 или cp1251 | До 30 000 знаков |

- Проверки делаются сразу при загрузке, до создания попытки, поэтому отказ попытку не расходует.
- В DOCX учитываются растровые изображения JPEG и PNG, вставленные в основной текст документа. Текст и изображения передаются на проверку в порядке элементов документа. Если таких изображений больше 5, DOCX отклоняется целиком — лишние изображения не отбрасываются молча. Встроенное изображение другого формата или изображение, которое не удаётся декодировать, также даёт отказ с просьбой заменить его на JPEG/PNG. Каждое изображение проходит проверку лимита пикселей Pillow из раздела 7.1, декодируется и уменьшается по одному; все пять исходников одновременно в памяти не хранятся. Фигуры, диаграммы Word и графика в колонтитулах на проверку не передаются: если они содержат часть решения, студент должен вставить их скриншот JPEG/PNG в основной текст.
- Тип файла проверяется по содержимому, а не по расширению.
- В `TESTING.md` для DOCX предусматриваются: пять изображений JPEG/PNG с проверкой порядка текста и картинок; шесть изображений; неподдерживаемый и повреждённый формат; графика в колонтитуле и фигуры Word; изображение сверх лимита пикселей; одновременный разбор двух DOCX с предельными изображениями под контролем памяти.
- Разбор файла при загрузке идёт в потоке через семафор `upload_parse` (2 одновременно), с ограничениями из раздела 7.1. Третья загрузка ждёт; если ожидание дольше 30 с — ответ «Сервер занят, повторите через минуту», попытка не расходуется.
- Системная часть запроса (общие инструкции преподавателя, условие, эталон, критерии, типичные ошибки) — не больше 12 000 знаков в сумме. Общие инструкции редактируются в «Настройки → Проверка домашних заданий ИИ» и сохраняются в `settings.grading_instructions`; техническое ядро запроса и схема JSON остаются неизменяемыми. Изменения применяются к следующим проверкам.

### 8.3. Запрос и ответ

Запрос: `POST {PROXYAPI_BASE_URL}/chat/completions`, заголовок `Authorization: Bearer {PROXYAPI_KEY}`, `model = MODEL_GRADING`, `temperature 0.2`, `max_completion_tokens 1500`, `reasoning_effort = low`. Служебные задачи используют тот же `reasoning_effort` и `max_completion_tokens 2000`: фактическая проверка 23.11.2026 показала, что при 800 токенах модель могла израсходовать весь лимит на рассуждения и вернуть пустой `content` с `finish_reason=length`. В системном сообщении — роль проверяющего, условие, эталон, критерии, типичные ошибки, шкала 0–10 и правила сравнения. Заполненное поле `criteria` объявляется исчерпывающим списком оценки: требования из условия, эталона и ранее проверенных работ не добавляются. При пустом `criteria` основой служат условие и эталон. В пользовательском — текущая работа и, при наличии, пакет ранее проверенных работ для сравнения.

Ответ — строго JSON:

```json
{
  "verdict": "accept | revise",
  "score": 0,
  "errors": [{"criterion": "", "description": "", "severity": "low | medium | high"}],
  "classification": "",
  "confidence": 0.0,
  "comment_for_student": "",
  "similarity_matches": [{"reference_id": 12, "match_percent": 0.0}]
}
```

- `similarity_matches` содержит ровно один результат для каждой работы сравнения в текущем пакете: `reference_id` — ID работы, `match_percent` — число от 0 до 100. Для сравнения выбираются последние проверенные преподавателем попытки других студентов по тому же заданию. В модель передаются только ID и подготовленное содержимое, без ников. Все подходящие работы разбиваются на пакеты до четырёх; текущая работа передаётся в каждом пакете. После каждого ответа сохраняются прогресс и суммарные `tokens_in`/`tokens_out`. При паузе по балансу завершённые пакеты не повторяются. Итоговый список, максимум, число сравнений и число недоступных файлов сохраняются в `submissions.similarity_json`; ники подставляются только при показе преподавателю. Процент не меняет автоматически вердикт или баллы.
- `score` — целое число от 0 до 10, иначе ответ считается невалидным.
- Невалидный JSON → одна повторная попытка, потом `needs_review`.
- `confidence < threshold` → `needs_review`, иначе `awaiting_approval`.
- Тайм-аут запроса 120 с.
- Ответы ProxyAPI обрабатывает общий клиент `proxyapi.py` — раздел 8.4.
- Из `usage` ответа записываются `tokens_in`, `tokens_out`, `model`, `cost_est` по ценам из настроек.

### 8.4. Ответы ProxyAPI: одна таблица для всех задач GPT

| Ответ | Что делает сайт |
|---|---|
| 200 | Результат сохраняется |
| 400, 404, 413, 422 | Ошибка самого запроса. Без повторов: задача `failed` с текстом ошибки в админке; работа студента → `needs_review` |
| 401 | Ключ отклонён. `gpt_stopped = True`: все задачи GPT останавливаются и ждут в очереди, письмо «ключ ProxyAPI отклонён». Снимается кнопкой «Проверить ключ» после правки `.env` и перезапуска |
| 402 | Нет средств. Задача → `paused_no_funds`, повтор не тратится, пауза (раздел 9) |
| 403 | Доступ запрещён (модель недоступна ключу или ограничение ключа). Как 401, письмо «ключ ProxyAPI: нет доступа к модели» |
| 429 | Слишком много запросов. Повтор через `Retry-After` секунд, если заголовок есть, иначе через 60 с. Не больше 5 повторов, потом `needs_review` |
| 5xx, сетевая ошибка, тайм-аут | До 3 повторов через 30 с, 2 мин, 10 мин; потом `needs_review` |
| Невалидный JSON или `score` вне 0–10 | Один повтор, потом `needs_review` |

Для пробной отправки при паузе действует та же таблица с одним отличием: сетевая ошибка, 5xx и 429 не меняют работу — пауза сохраняется, проба повторяется через 15 минут.

### 8.5. Повторный платный запрос после сбоя

Очередь выполняет задачу «не меньше одного раза» (at-least-once). Если сервер перезапустится после отправки запроса, но до сохранения ответа, ProxyAPI мог уже списать оплату. Механизм повторной отправки без повторной оплаты (idempotency key) в документации ProxyAPI не описан, поэтому сайт на него не рассчитывает.

Аналогичная неопределённость возникает при тайм-ауте или позднем 5xx: модель могла завершить работу до потери ответа. Автоматические повторы из раздела 8.4 сохраняются для доступности сервиса и **могут привести к повторной оплате**. Защита ниже ограничивается только автоматическим повтором после перезапуска; ручная кнопка «Проверить ИИ снова» также создаёт новый платный запрос. Этот остаточный риск фиксируется в `TESTING.md`, а полный запрет дублирования расхода обеспечивается только бюджетом ключа.

- Перед отправкой в `jobs.request_sent_at` записывается время, отдельной транзакцией.
- При старте задача `grading` в статусе `running` с заполненным `request_sent_at` **не отправляется повторно**: работа получает `needs_review` с пометкой «ответ ИИ потерян при перезапуске сервера». В экране работы есть кнопка «Проверить ИИ снова».
- Дешёвые задачи `parse_abbr`, `abbr_guess`, `source_meta` при перезапуске повторяются: лишний расход — доли рубля.
- Тест в `TESTING.md`: прервать процесс после отправки запроса к заглушке ProxyAPI и убедиться, что повторной отправки нет.

## 9. Баланс ProxyAPI

Модуль `services/balance.py`. Описание функции — `01-FUNCTIONS.md`, раздел 11.

**Запрос баланса:** `GET {PROXYAPI_BALANCE_URL}` с заголовком `Authorization: Bearer {PROXYAPI_KEY}`, тайм-аут 10 с. Ответ:

```json
{"balance": 1234.56}
{"balance": 37.66, "budget": {"limit": 50.0, "used": 12.34}}
```

Второй вариант — у ключа с бюджетом: `balance` — остаток бюджета ключа ([ProxyAPI, баланс](https://www.proxyapi.ru/docs/balance)). Каждый ответ записывается в `balance_log`.

**Ошибки запроса баланса:**

- 401 → `last_error = key_rejected`, `gpt_stopped = True`, письмо преподавателю;
- 403 → `balance_access = denied`, монитор показывает подсказку «включите у ключа разрешение «Запрос баланса»»;
- сеть, 429 или 5xx → значение не меняется, в мониторе «нет связи с ProxyAPI с <время>».

**Резерв на проверку** — оценка с запасом, а не гарантированный максимум. Точное число токенов до запроса узнать нельзя: токенизатора модели на сервере нет, а картинки тарифицируются по правилам модели. Единственный жёсткий предел расхода — бюджет ключа в кабинете ProxyAPI.

```
tokens_in_est(работа) = ceil((знаков системной части + знаков работы) / 2) + 500
                        + картинок × image_tokens            # image_tokens из check_models, по умолчанию 1500
cost_est(работа)      = (tokens_in_est × price_in + 1500 × price_out) / 1e6
check_reserve         = cost_est(худший случай: 12 000 + 30 000 знаков + 5 изображений) × reserve_factor   # reserve_factor = 1,5
```

- Делитель 2 знака на токен взят с запасом для русского текста.
- При ценах из раздела 8.1 и `image_tokens = 1500`: текстовая работа без картинок — `21 500 × 260 / 1e6 + 1500 × 1300 / 1e6 = 7,54 ₽`, её резерв — 11,31 ₽. Худший случай с пятью изображениями (сканами PDF или картинками DOCX) — `(21 500 + 5 × 1500) × 260 / 1e6 + 1500 × 1300 / 1e6 = 9,49 ₽`, его `check_reserve = 14,24 ₽`, на экране — **15 ₽**. Для единого порога паузы используется именно этот худший случай.
- После 20 проверок монитор показывает отношение фактических `usage.prompt_tokens` к `tokens_in_est`. Если оно больше 1, преподаватель увеличивает `reserve_factor` в настройках. После изменения модели или цен пример пересчитывается автоматически, а `check_models` повторяется.

**Уровень:**

```
level = no_funds  если paused
        unknown   если balance_access ≠ allowed или последний успешный ответ (last_ok_at) старше 2 ч
        no_funds  если balance < check_reserve
        critical  если balance < balance_critical   (по умолчанию 100)
        low       если balance < balance_low        (по умолчанию 300)
        ok        иначе
```

При `unknown` пороги «мало» и «критично» не вычисляются: монитор показывает «баланс неизвестен» и время последнего успешного ответа, письма об уровнях не отправляются. Задачи GPT идут, пока ProxyAPI не ответит 402.

**Пауза:**

- `paused = True`, когда ProxyAPI ответил 402 или известный баланс меньше `check_reserve`.
- При паузе задачи с GPT (`grading`, `parse_abbr`, `abbr_guess`, `source_meta`) не отправляются, получают `paused_no_funds`.
- **Снятие паузы, запрос баланса разрешён:** баланс проверяется каждые 5 минут. Если `balance ≥ check_reserve`, пауза снимается.
- **Снятие паузы, запрос баланса не разрешён:** каждые 15 минут первая задача из очереди отправляется как пробная. 402 → пауза продолжается, ProxyAPI ничего не списывает. Успешный ответ → результат сохраняется как обычно, пауза снимается.
- Кнопка «Возобновить сейчас» в мониторе делает пробную отправку сразу.
- После снятия паузы задачи `paused_no_funds` возвращаются в `queued` по порядку создания. Письмо «Баланс восстановлен, в очереди N задач».

**Расход и прогноз:**

- расход за период — сумма `cost_est` из `jobs` за период. Это оценка по токенам и ценам из настроек, а не точное списание;
- средняя стоимость проверки — среднее `cost_est` последних 20 задач `grading`;
- прогноз в проверках — `balance / средняя стоимость проверки`;
- прогноз в днях — `balance / средний расход в день за 7 дней`. Если данных меньше 3 дней, прогноз не показывается.

**Письма:** при переходе на уровень `low`, `critical`, `no_funds` и при восстановлении. Повтор того же уровня — не чаще раза в 12 часов (`balance_alerts`). Тема — «hwstud: баланс ProxyAPI — <уровень>», в тексте баланс, прогноз, число задач в очереди, ссылка на монитор.

**Страница монитора** `/admin/settings/proxyapi`: данные из `balance_log`, `balance_state` и `jobs`. График за 30 дней — SVG, который сервер строит в шаблоне, без библиотек. Кнопка «Пополнить баланс» — ссылка из настройки `billing_url`; пока она пустая — `https://proxyapi.ru`.

## 10. Фоновая работа: очередь, потоки, расписание

### 10.1. Почему потоки

PyMuPDF, python-pptx, python-docx, openpyxl, `smtplib` и резервное копирование SQLite работают синхронно. Если вызывать их прямо в цикле `asyncio`, сайт перестанет отвечать на время их работы. Поэтому:

- все синхронные операции вызываются через `asyncio.to_thread(...)`;
- число одновременных операций каждого вида ограничено семафорами:

| Семафор | Что входит | Одновременно |
|---|---|---|
| `heavy` | Импорт лекции, выгрузки PDF/DOCX/XLSX, архивы, копии базы, `VACUUM` и удаление данных студентов | 1 |
| `upload_parse` | Разбор загружаемой работы студента (PyMuPDF, python-docx, Pillow) | 2 |
| `gpt` | Запросы к ProxyAPI | 2 |
| `mail` | Отправка писем | 1 |

- Запросы httpx к ProxyAPI асинхронные (`httpx.AsyncClient`), в поток их выносить не нужно.
- В каждом потоке своё подключение к SQLite. Подключения между потоками не передаются.

### 10.2. Очередь `jobs` и приоритеты

Цикл раз в 2 секунды выбирает следующую задачу с наименьшим `priority`, а при равном — самую раннюю.

| Приоритет | Вид задачи | Когда выполняется |
|---|---|---|
| 1 | `mail` — письма преподавателю (сообщения, баланс) | Сразу |
| 2 | `lecture_import` — разбор PPTX + PDF | Сразу, по одному |
| 3 | `grading` — проверка работ | Сразу, до 2 одновременно |
| 4 | `parse_abbr`, `abbr_guess` — сокращения при импорте | После проверок работ |
| 5 | `source_meta` — тип и аннотация источника | После разбора сокращений |
| 6 | `export` — выгрузки и архив работ по кнопке; `delete_temp` — удаление временного архива | `export` по кнопке, `delete_temp` по `run_after`; через `heavy` |

**Защита от повторного выполнения:** задача забирается одним запросом:

```sql
UPDATE jobs SET status='running', started_at=:now
WHERE id = (SELECT id FROM jobs WHERE status='queued' AND run_after <= :now
            ORDER BY priority, id LIMIT 1)
RETURNING *;
```

Результат задачи и смена её статуса на `done` записываются одной транзакцией. Повторный запуск задачи с `status = done` невозможен.

**Восстановление после перезапуска:** при старте приложения задачи в статусе `running` возвращаются в `queued` с `tries + 1`, кроме `grading` с заполненным `request_sent_at` (раздел 8.5). После 5 неудачных запусков задача получает `failed` и видна в админке. Работа студента при этом получает `needs_review`.

### 10.3. Расписание

| Задача | Время (МСК) | Семафор |
|---|---|---|
| Запрос баланса ProxyAPI | Каждые 30 мин; каждые 5 мин при паузе | — |
| Пробная отправка при паузе без доступа к балансу | Каждые 15 мин | `gpt` |
| Сводное письмо о сообщениях | Каждый час в 00 мин, если включено или превышен порог 30 писем | `mail` |
| Публикация и снятие объявлений по дате | Каждую минуту | — |
| Копия базы (`sqlite3` API `backup`) | Ежедневно 03:30 | `heavy` |
| Архив «база + лекции» | Воскресенье 04:00 | `heavy` |
| Проверка свежего архива: распаковка во временную папку, `PRAGMA integrity_check`, число строк в главных таблицах | Воскресенье 04:15 | `heavy` |
| Удаление временного архива работ | Задача `delete_temp` с `run_after = created_at + 1 час`; контрольная очистка просроченных файлов при старте | `heavy` |
| Очистка: завершённые импорты, просроченные предпросмотры, временные архивы работ, старые копии | Ежедневно 04:30 и при старте | `heavy` |

Ночные задачи стоят на 03:30–04:30, когда студенты почти не заходят. Если в это время идёт импорт лекции, ночная задача ждёт освобождения семафора `heavy`.

uvicorn запускается строго с одним worker: очередь и расписание живут внутри этого процесса.

## 11. Почта

- `smtplib.SMTP_SSL` на порт 465 или `SMTP` + `starttls()` на порт 587 — по настройке в `.env`. Порт 25 не используется.
- Настройки SMTP берутся только из `.env` и меняются только правкой файла на сервере и перезапуском. Веб-формы для пароля нет.
- Письмо о сообщении: тема «hwstud: вопрос от <ник>, <группа>», текст, ссылка на ветку в админке.
- Режим писем: «сразу» (по умолчанию) или «сводка раз в час». После 30 писем о сообщениях за сутки сайт до 00:00 переходит на сводку.
- Ошибка отправки не мешает сохранить сообщение: письмо остаётся в `jobs` с повтором через 5, 15, 60 мин.
- Кнопка «Отправить пробное письмо» в настройках.

## 12. Резервные копии и удаление данных

- **Ежедневно 03:30:** копия базы через `sqlite3` API `backup` в `data/backups/hwstud-YYYYMMDD.db`. Хранятся 14 последних.
- **Воскресенье 04:00:** архив «база + лекции» `data/archives/site-YYYYMMDD.tar.gz`. В архив кладётся только что сделанная согласованная копия базы, а не рабочий файл `hwstud.db`, плюс папка `data/lectures/`. Хранятся 2 последних архива. Работы в этот архив не входят.
- **Архив работ** собирается только по кнопке «Скачать архив работ» во временный файл `data/tmp/works-<время>.zip`. Одновременно хранится не более одного такого архива: повторный запрос сначала завершает новый архив во временном имени, затем атомарно заменяет прежний и удаляет старый файл. Вместе с архивом создаётся задача `delete_temp` с `run_after = created_at + 1 час`; она удаляет именно записанный в её `payload_json` путь, скачан файл или нет. При замене архива старая задача `delete_temp` отменяется. Просроченные временные файлы дополнительно удаляет очистка при старте приложения.
- **Проверка архива** в воскресенье 04:15: результат («архив от <дата> проверен» или ошибка) виден в «Данных курса» и при ошибке уходит письмом.

### 12.1. Удаление данных студентов

Порядок выбран так, чтобы у сайта всё время оставалась хотя бы одна резервная копия, а прерванное удаление продолжалось после перезапуска. Шаг записывается в `maintenance.deletion_step`. На всё время операции закрываются студенческие маршруты, загрузка работ, сообщения и создание новых фоновых задач студентов; преподавателю доступна только страница состояния удаления.

1. **Удаление строк — транзакция SQLite:** удаляются `students`, `submissions`, `messages`, `threads`, `announcement_reads`, `slide_views`, `review_requests`, связанные `jobs`, в том числе `export` и `delete_temp`. В `audit_log` у записей с `student_id` поля `actor`, `object`, `details_json` заменяются на «удалённый студент», `student_id = null`. В коде запрещено писать ник в `audit_log` иначе как через поле `student_id` и `actor`. После фактического удаления строк в этой же транзакции устанавливается `deletion_step = db_deleted` и выполняется commit. **`VACUUM` внутрь этой транзакции не входит.**
2. **Физическая очистка базы — вне транзакции удаления:** под семафором `heavy` выполняются `VACUUM`, затем `PRAGMA wal_checkpoint(TRUNCATE)`. После успешного завершения устанавливается `deletion_step = db_done`. `PRAGMA secure_delete = ON` уже установлен на каждом подключении в `db.py` (раздел 3), а не только однократно на этом шаге. Если процесс прервётся, из `db_deleted` операция повторяет только этот шаг очистки.
3. **Новая копия:** создаются копия базы и архив «база + лекции» без данных студентов с уникальным суффиксом UTC-даты и времени, например `hwstud-YYYYMMDD-HHMMSS-cleanup.db` и `site-YYYYMMDD-HHMMSS-cleanup.tar.gz`, поэтому они не перезаписывают плановые копии того же дня. Выполняется `integrity_check` новой базы и контрольное чтение архива. Только после успеха устанавливается `deletion_step = backup_done`.
4. **Старые данные:** удаляются `data/uploads/`, `data/tmp/`, все прежние копии в `data/backups/` и архивы в `data/archives/`, кроме созданных на шаге 3. Затем устанавливается `deletion_step = files_done`.
5. В `audit_log` добавляется запись «данные студентов удалены» без ников, `deletion_step` становится `null`. После этого студенческие маршруты снова доступны.

При старте приложение смотрит `deletion_step` и продолжает с соответствующего незавершённого шага: `db_deleted` → очистка базы, `db_done` → новая копия, `backup_done` → удаление файлов, `files_done` → завершающая запись. Пока шаг не стал `null`, удаление считается незавершённым.

### 12.2. Восстановление из копии

Описывается в `DEPLOY.md` командами и проверяется один раз до начала курса на чистом каталоге (сценарий в `TESTING.md`):

1. `systemctl stop hwstud`.
2. Распаковать архив «база + лекции» в `DATA_DIR` (`tar -xzf`); при восстановлении только базы — положить файл копии как `data/hwstud.db`.
3. Проверить: `sqlite3 data/hwstud.db "PRAGMA integrity_check;"` → `ok`.
4. `systemctl start hwstud`, войти в админку, открыть лекцию в режиме студента.

Работы студентов из архива сайта не восстанавливаются: их архив преподаватель хранит у себя после скачивания.
